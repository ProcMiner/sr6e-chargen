# SR6e Character Generator — CLAUDE.md

A Shadowrun 6th Edition character generator and live-play companion, built for a small private group of friends (not a public product). Two people GM concurrent campaigns; everyone else plays. Solo side project, actively developed.

Live at https://procminersgaming.tools/sre6-chargen (landing page at the domain root, ahead of more TTRPG tools planned there later).

## Stack & layout

npm workspaces monorepo, two packages:

- **`client/`** — React 19 + React Router 7 + Vite + TypeScript. One hand-written stylesheet, `client/src/index.css` (~1300 lines) — no CSS framework, no component library. Restyle/extend existing class names rather than inventing a parallel set.
- **`server/`** — Express + better-sqlite3, TypeScript. SQLite DB at `server/data/chargen.sqlite` (WAL mode).

Root-level commands (from repo root):

```bash
npm run dev      # both client (:5173) and server (:3001) concurrently
npm run build    # server tsc, then client tsc -b && vite build
```

**Always run the full `npm run build` before considering a change done, not just `tsc --noEmit`.** Dev-mode Vite tolerates things the production build's LightningCSS minifier rejects outright — e.g. a CSS comment containing a literal `*/` mid-string closes early under minification but is silently fine in dev. Caught this exact bug once; don't reintroduce the class of bug by skipping the real build.

Client lint: `npx oxlint` (from `client/`).

## Architecture conventions

- **No dice-rolling engine anywhere.** Damage, Edge, and Karma are always player-reported from the table, never generated by the app. Opposed/extended tests stay reference formulas (tables, dice-pool math shown to the player) — only what's directly computable from a character's own attributes/gear (Attack Rating, Initiative, Matrix Attributes, etc.) is a real computed number.
- **`derive*.ts` files** (`client/src/derive*.ts`, `deriveGear.ts`, `deriveQualities.ts`, etc.) are pure functions taking `CharacterData` (+ rules catalogs where needed) and returning computed values. Reuse these rather than recomputing inline — several past bugs came from one call site duplicating a calculation that drifted from the canonical one (see the Karma-pool/Prime-Runner fix in git history for a concrete example).
- **`CharacterData`** (chargen build: attributes, skills, gear, qualities, etc.) is separate from **`PlayState`** (`character_play_state` table: damage, Edge available, status effects) — PlayState is session-transient and written every few seconds during play; CharacterData is the durable build.
- **Priority System and Life Path** are two parallel chargen flows (`pages/builder/PriorityBuilder/`, `pages/builder/LifepathBuilder/`) that share a common tail of steps (Qualities → Customization Karma → Buy Gear → Finishing → Final Calculations) via `pages/builder/sharedSteps/tailSteps.tsx`.
- **Rules catalogs** (qualities, spells, gear, adept powers, etc.) live server-side in `server/src/rules/*.ts` and are served via `/api/rules/*`, typed in `client/src/rules.ts`.
- **GM's Bar** (`pages/play/GmDashboard.tsx`) can write to a session member's `PlayState` even when the GM doesn't own that character — auth is owner-OR-session-GM for the play-state endpoints specifically (`server/src/routes/characters.ts`'s `ownedOrGmCharacter`/`isSessionGmFor`). Every other character endpoint (the chargen `data` blob, deletion, rename) stays owner-only.
- **Design system**: Nocturne — dark ground (`--color-bg: #161826`), single blurple accent (`--color-accent: #9184d9`), Inter typeface, 0.7x-density spacing scale, 8px radii. Full token set at the top of `client/src/index.css`; legacy token names (`--bg`, `--panel`, `--accent`, etc.) are kept as aliases onto the new tokens rather than renamed everywhere, so old and new rules coexist. New CSS should use `--color-*`/`--space-*`/`--radius-*` directly. No light theme.

## Scope boundaries (deliberate, not gaps)

This app is a character generator + live-play tracker, not a full VTT. It deliberately does not implement: combat/Matrix/rigging dice resolution (the "no dice engine" rule above), GM advice/setting lore, Availability-based legality enforcement, or full vehicle/rigger test simulation. When rules content is genuinely out of scope, `client/public/rules-coverage.html` says so explicitly rather than leaving it silently unimplemented — check there before assuming something's missing by accident.

## Deployment

Single Lightsail instance, systemd service `chargen`, Caddy reverse-proxying HTTPS. From a machine with SSH access configured:

```bash
ssh <lightsail-host> "sudo -u chargen bash -lc 'cd /opt/sr6e-chargen/app && git pull && npm install && npm run build' && sudo systemctl restart chargen"
```

**Workflow expectation**: after committing, ask before pushing to master rather than stopping silently — but once pushed, redeploy to the live server automatically without waiting to be asked again. Never `--force` push to master.

## Things that only work from a machine with local setup (not portable to a fresh clone/cloud session)

- **Deploying**: the SSH key/host alias for the Lightsail box is local machine config, not in this repo. A session without it can commit and push code but can't redeploy — flag this rather than silently failing to ship.
- **Sourcebook PDFs**: the actual SR6E rulebook PDFs (core + ~10 sourcebooks) used to verify rules content are local files on the maintainer's desktop, **not checked into this repo** (too large, and mostly copyrighted scans). A session without them should say so rather than guessing at rules text from training data alone — this project has a strong preference for verifying against source over recalling from memory.
- **Local dev DB**: `server/data/chargen.sqlite` (gitignored) accumulates real test characters/users over time on the maintainer's machine. A fresh clone starts with an empty DB — register a new test user rather than assuming any specific credentials exist.

## Working style notes

- User tests hands-on on iPad Safari and desktop; bug reports tend to be precise and incremental — take each detail in a report literally rather than looking for a broader pattern that isn't stated.
- Prefer verifying claims (rules text, DB state, live site behavior) over asserting from memory — this project has caught real bugs (e.g. a Karma-pool initialization bug, a CSS comment breaking only the production build) specifically by checking rather than assuming.
